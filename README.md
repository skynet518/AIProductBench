# AIProductBench

**A lightweight, reproducible benchmark for comparing LLMs on real AI product work.**

AIProductBench V0.1 runs 10 practical product-management tasks across 3 capability
domains against 2 models, scores every response with a single LLM-as-Judge, and
reports quality alongside the operational cost of running the models: tokens,
latency, and estimated spend.

> **Honest positioning.** This is an early, deliberately small, practical benchmark.
> Ten cases and one run per case make the results indicative, not statistically
> robust. It is a clear and reproducible comparison, not a scientific evaluation.

## What V0.1 contains

| Element | V0.1 |
| --- | --- |
| Test cases | 10 |
| Capability domains | 3 |
| Evaluated models | 2 (Qwen 3.7 Flash, DeepSeek V4 Flash) |
| Judge | 1 (Qwen 3.7 Max) |
| Metrics | score, input/output/total tokens, estimated cost, latency |
| Artifacts | `sample_results.json`, `leaderboard.html`, `README.md` |
| Dependencies | `requests` |
| Storage | JSON files, no database, no backend, no frontend framework |

## Repository layout

```
.
```

Model IDs, endpoints, API-key environment variables, and prices live only in
[`src/config.py`](src/config.py). No benchmark logic hard-codes a provider.

## Quickstart

Requires Python 3.10 or newer.

```bash
pip install -r requirements.txt

export DASHSCOPE_API_KEY=...   # Qwen 3.7 Flash candidate + Qwen 3.7 Max judge
export DEEPSEEK_API_KEY=...    # DeepSeek V4 Flash candidate

python3 run_benchmark.py --validate-only   # checks config + the 10 cases, no network
python3 run_benchmark.py --estimate        # projected call count and API cost, no network
python3 run_benchmark.py --dry-run         # full pipeline offline, synthetic output only
python3 run_benchmark.py --confirm         # real run against both providers
```

Credentials are read from environment variables only. This project never reads
API keys from Codex configuration files or any other file on disk, and `.env` is
git-ignored.

### The paid-run gate

A real run **refuses to start without `--confirm`**. Running the benchmark with no
flags prints the projected API call count and cost and then stops:

```
$ python3 run_benchmark.py
  candidate model calls : 20 (10 cases x 2 models)
  judge calls           : 20
  total API calls       : 40
  ...
  Stopped before spending. Re-run with --confirm once the projected
  cost above has been reviewed and approved.
```

This gate exists so that spending is always reviewed first. `--dry-run` makes no
network calls and incurs no cost.

## Models and reproducibility

Model IDs, endpoints, and prices are configured in one place: the
`MODELS`, `JUDGE`, and pricing blocks of [`src/config.py`](src/config.py).

| Role | Display name | API model ID | Reproducibility |
| --- | --- | --- | --- |
| Candidate A | Qwen 3.7 Flash | `qwen3.7-flash-2026-07-15` | Pinned snapshot, 2026-07-15 |
| Candidate B | DeepSeek V4 Flash | `deepseek-v4-flash` | API model ID is not a dated snapshot |
| Judge | Qwen 3.7 Max | `qwen3.7-max-2026-05-20` | Pinned snapshot, 2026-05-20 |

Both Qwen models are pinned to dated snapshots rather than rolling aliases, so a
run can be repeated against the same weights.

**DeepSeek is not date-pinned.** The public DeepSeek API model ID
`deepseek-v4-flash` is not a dated snapshot, so this project does not represent
it as one. The documented underlying model version at the pricing snapshot date
is recorded for reference as `DeepSeek-V4-Flash-0731`.

> Note: `deepseek-flash` was the name used by a local Codex model catalog. It is
> **not** the official DeepSeek API model ID and is not used for benchmark calls.
> This project calls `deepseek-v4-flash`.

Every model ID can be overridden without editing code — `AIPB_MODEL_QWEN`,
`AIPB_MODEL_DEEPSEEK`, `AIPB_JUDGE_MODEL`, `AIPB_BASE_URL_*`, and
`AIPB_WIRE_API_*`.

## Test cases

Every case carries an `id`, a `domain`, a `prompt`, and explicit
`evaluation_criteria` that the judge uses alongside the shared rubric.

| ID | Domain | Case |
| --- | --- | --- |
| IF-01 | instruction_following | Messy request to kickoff problem statement |
| IF-02 | instruction_following | Release notes under hard constraints |
| IF-03 | instruction_following | One update, three audiences, facts preserved |
| IF-04 | instruction_following | Clarify instead of building |
| PR-01 | product_reasoning | Backlog prioritization with a stated rule |
| PR-02 | product_reasoning | Measurement plan with rollback thresholds |
| PR-03 | product_reasoning | Go or no-go on the launch data |
| SA-01 | structured_analysis | Messy support ticket to fixed schema |
| SA-02 | structured_analysis | Pick a configuration from a results table |
| SA-03 | structured_analysis | Interview transcript to opportunity map |

Distribution: instruction_following 4, product_reasoning 3, structured_analysis 3.
Every prompt is self-contained, and every case is scoped to work a product team
actually does: prioritising, measuring, deciding, and structuring messy input.

## Capability domains

| Domain | What it measures |
| --- | --- |
| `instruction_following` | Obeying explicit format, length, tone, and negative constraints while staying faithful to the source material. |
| `product_reasoning` | Making and justifying product decisions: prioritisation, measurement design, launch judgment. |
| `structured_analysis` | Turning messy or tabular input into a fixed, machine-readable structure without inventing facts. |

## Judge and rubric

One judge model evaluates every response. It receives **both** the shared rubric
and the case-specific `evaluation_criteria`, and the case-specific criteria are
authoritative where they are more concrete.

Exactly three shared dimensions are scored, each as an integer from 1 to 5:

| Dimension | Question |
| --- | --- |
| `task_completion` | Did the response fully do what the case asked, using only the information given? |
| `instruction_following` | Did it obey every explicit constraint, including negative ones? |
| `quality_usefulness` | Would an experienced PM find it specific and decision-ready? |

**Aggregation.** The overall score is the equal-weight mean of the three
dimensions, normalised to 0-100:

```
mean       = (task_completion + instruction_following + quality_usefulness) / 3
overall    = (mean - 1) / (5 - 1) * 100
```

**Strict output.** The judge must return machine-readable JSON. Output is parsed
strictly and is never silently repaired: a missing dimension, an unexpected
dimension, a non-integer score, a score outside 1-5, or an empty rationale is
reported as a failure so the result is visibly incomplete rather than quietly
plausible. The raw judge output is preserved in the results for inspection.

### Judge bias is a known V0.1 limitation

The judge belongs to the **Qwen family**, and one of the two evaluated models
(Qwen 3.7 Flash) is also from that family. Judge-family bias — including
self-preference toward in-family responses — **cannot be ruled out** in V0.1 and
may inflate the Qwen candidate's scores. Read the leaderboard with that in mind.
A cross-family judge is a planned improvement, not a V0.1 feature.

## Metrics

For every evaluated response, the results record:

| Field | Definition |
| --- | --- |
| `judge.mean_score` | Mean of the three rubric dimensions, 1-5 |
| `judge.normalized_score` | Mean rescaled to 0-100 |
| `judge.scores` | Per-dimension integer scores |
| `judge.rationale` | Judge's short written justification |
| `input_tokens` / `output_tokens` / `total_tokens` | Usage reported by the provider API |
| `estimated_cost_usd` | Derived from reported tokens and the dated pricing snapshot |
| `latency_ms` | Wall-clock time for the model call |
| `model_key` / `model_id` | Which model produced the response |
| `case_id` / `domain` | Which test case and capability domain |

**No metric is ever fabricated.** When a provider does not report usage, the
value is `null` rather than estimated, and the cost is `null` with it. Estimated
token counts appear only in the `--estimate` projection, which is clearly
labelled as a planning estimate and never written into results.

## Cost accounting

Candidate inference cost and judge evaluation cost are tracked **separately**:

- **`candidate_cost_usd`** — inference cost of the two evaluated models. This is the
  headline cost on the leaderboard.
- **`judge_cost_usd`** — evaluation overhead for the LLM-as-Judge, reported on its
  own line so it never inflates a model's cost figure.

### Pricing snapshot — 2026-09-11

Official provider **list pricing only**. Promotional and discounted rates are
excluded. All rates are USD per 1,000,000 tokens.

**Qwen (Alibaba Cloud Model Studio).** Qwen rates are region-specific, so the
region is resolved from the configured DashScope base URL rather than assumed.
The configured base URL is `https://dashscope.aliyuncs.com/compatible-mode/v1`,
which is the **China (Beijing)** region. If the base URL is changed to
`dashscope-intl.aliyuncs.com`, the Singapore rates are used automatically. If the
base URL cannot be mapped to a known region, pricing is reported as unresolved
instead of guessed.

| Model | Region | Input / 1M | Output / 1M |
| --- | --- | --- | --- |
| Qwen 3.7 Flash | China (Beijing) | $0.028 | $0.11 |
| Qwen 3.7 Max | China (Beijing) | $1.65 | $4.951 |
| Qwen 3.7 Flash | Singapore | $0.03 | $0.13 |
| Qwen 3.7 Max | Singapore | $2.50 | $7.50 |

The Qwen 3.7 Flash rates above are valid **only for requests with input at or
below 32K tokens**. If an actual request exceeds that tier, cost estimation fails
explicitly for that call and the cost is recorded as `null`; the tool never
applies a rate that does not match the request.

**DeepSeek (DeepSeek API).** DeepSeek prices by time of day. Peak hours are
01:00-04:00 and 06:00-10:00 UTC, Monday through Friday; all other times are
off-peak. Peak window boundaries are treated as start-inclusive, end-exclusive.

| Window | Cache-miss input / 1M | Output / 1M |
| --- | --- | --- |
| Off-peak | $0.22 | $0.66 |
| Peak | $0.44 | $1.32 |

DeepSeek cache-hit token accounting is not used in V0.1, so input cost is
calculated **conservatively with cache-miss pricing**. This is documented in the
pricing metadata and on the leaderboard.

Sources recorded in the price metadata: *Alibaba Cloud Model Studio — qwen3.7-flash
Model Info*, *Alibaba Cloud Model Studio — qwen3.7-max Model Info*, and *DeepSeek
API Docs — Models & Pricing*.

## Results and artifacts

- **`sample_results.json`** — the canonical committed result, produced by an
  approved real run. It contains run metadata, the rubric, the models, the judge,
  the pricing snapshot, one record per case per model, and the aggregated summary.
- **`leaderboard.html`** — generated from that JSON. It is a single self-contained
  file: inline CSS and inline data, no CDN, no JavaScript, no build step. Open it
  directly from disk.
- **`results/`** — local, git-ignored output. Dry runs write here.

Both committed artifacts require a real paid run and are therefore **not present
yet**. Dry-run output is written only to `results/`, is flagged `synthetic: true`
throughout, and is bannered "SYNTHETIC DRY-RUN" so it can never be mistaken for a
real result. A dry run never overwrites `sample_results.json` or `leaderboard.html`.

## Validation

`python3 run_benchmark.py --validate-only` checks, with no network access:

- all 10 test cases load and the JSON is valid
- exactly 3 domains exist, matching the configured domain list
- case IDs are unique and every case has a prompt and non-empty criteria
- exactly 2 evaluated models are configured, with distinct model IDs
- exactly 1 judge is configured, and it is not one of the evaluated models
- provider endpoints use HTTPS and wire APIs are supported
- which API key environment variables are present (presence only, never values)

`python3 run_benchmark.py --dry-run` exercises the whole pipeline offline with
deterministic synthetic responses, then verifies that judge JSON parses, that
aggregation runs, and that the leaderboard renders standalone.

## Usage, limitations, and scope

Known limitations, stated plainly:

- Small sample: 10 cases, one run per case, no repeated sampling.
- Judge-family bias: the judge shares the Qwen family with one evaluated model.
- Single-judge design: no voting, no human calibration, no other judge.
- Pricing is a manually curated snapshot, not a live billing figure.
- DeepSeek input cost assumes cache-miss pricing, the conservative choice, and
  DeepSeek spend varies with peak and off-peak run times.
- Qwen 3.7 Flash pricing covers requests at or below 32K input tokens only.
- DeepSeek is not date-pinned: its public API model ID is not a dated snapshot,
  so its underlying version can change between runs.
- Latency varies with provider load and network conditions and is not a controlled
  measurement.

Deliberately out of scope for V0.1: multiple judges, additional models or domains,
statistical significance testing, repeated trials, CI, containerisation, a web
backend, a database, and provider SDKs. These are candidates for later versions,
not V0.1 requirements.
